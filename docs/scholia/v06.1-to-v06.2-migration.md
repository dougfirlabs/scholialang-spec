# Scholia v0.6.1 → v0.6.2 migration guide

Scholia v0.6.2 corrects Rule 4, `action_recorded`, for recursive traces
whose result atoms appear in later steps. The atom catalog, parser
shape, operators, and validator report shape do not change.

## What changed

v0.6.1 recognizes a nested `<Finding>` or a later same-Step sibling.
That adjacency rule does not cover a common causal sequence:

1. an agent emits an `<Action>`;
2. a later step captures test output in `<Observation>` or
   `<Evidence>`; and
3. a still-later `<Finding>` records the result and explicitly
   `REFER`s the Action or the intermediate evidence.

v0.6.2 accepts that explicitly linked sequence. It also accepts a later
goal-closing `<Concluding>` that directly `REFER`s the Action, and an
optional graph view containing a `records_result` edge targeting the
Action.

For a non-immediate result, order alone is not provenance. A later
unlinked or unrelated Finding does not satisfy Rule 4.

## Producer guidance

The most portable result form directly names the Action:

```xml
<Step id="S_01">
  <Action id="Act_01">Applied the requested change.</Action>
</Step>
<Step id="S_02">
  <Observation id="Obs_01">The scoped tests completed.</Observation>
</Step>
<Step id="S_03">
  <Finding id="F_01">The tests passed. REFER:Act_01</Finding>
</Step>
```

An indirect result is also valid when the chain is explicit:

```xml
<Observation id="Obs_01">The tests passed. REFER:Act_01</Observation>
<Finding id="F_01">The result is verified. REFER:Obs_01</Finding>
```

Existing nested-descendant and immediate same-Step result forms remain
valid.

## Validator guidance

1. Flatten top-level atoms into trace document order while retaining
   same-Step adjacency.
2. Preserve nested and immediate same-Step result acceptance.
3. For a non-immediate later `<Finding>`, accept a direct
   `REFER:Action` or a one-hop `Finding → Observation|Evidence →
   Action` chain.
4. For a later `<Concluding>`, require both a direct `REFER:Action` and
   a non-empty `for_goal`.
5. If the validator accepts a graph view, accept a `records_result`
   edge targeting the Action.
6. Do not accept chronology alone for a non-immediate result.
7. Stamp `SCHOLIA_VALIDATOR_VERSION = "0.6.2"`.

The shared executable contract is
[`../../conformance/v0.6.2/action_recorded.json`](../../conformance/v0.6.2/action_recorded.json).
Implementation adapters should run the named Rule 4 expectation for
every case.

## Compatibility note

The change broadens Rule 4 for causally linked cross-step results. It
also corrects an over-broad v0.6.1 implementation behavior that could
accept any non-immediate later same-Step Finding based on order alone.
Such order-only traces must add an explicit `REFER` link in v0.6.2.
This is a validator-semantic correction, not a syntax or data-model
change.

## Downstream release order

1. Publish/tag this specification contract.
2. Port the fixtures and rule to the Python reference implementation.
3. Re-sync the MCP package's vendored validator and run the same suite.
4. Run host-tool parity checks against the shared cases.
5. Tag package releases only after all adapters agree on every expected
   Rule 4 outcome.
